# 밴드 공연 방명록 웹앱 설계

## 배경 및 목적

밴드 공연 당일, 관객이 QR/링크로 접속해 방명록을 남기고 서로의 글을 볼 수 있는
페이지를 하루 동안만 운영한다. 공연 중 무대 위에서 밴드가 그 시점까지 쌓인
글 중 하나를 실시간으로 무작위로 뽑아 보여주는 이벤트 기능이 핵심 요구사항이다.

- 운영 기간: 공연 당일 하루만
- 트래픽 규모: 공연 관객 수준 (수십~수백 건의 글 예상)
- 인프라 운영 부담을 최소화해야 함 (컴퓨터를 계속 켜둘 필요 없어야 함)

## 요구사항

1. 방문객은 이름, 전화번호 뒤 4자리, 메시지를 입력해 글을 남길 수 있다.
   - 전체 전화번호는 입력받지 않는다 (뒤 4자리만 수집).
2. 같은 이름 + 전화번호 뒤 4자리 조합으로는 글을 1개만 남길 수 있다.
   중복 작성 시도 시 "이미 방명록을 남기셨어요" 안내를 띄운다.
   - 이름의 모든 공백은 제거한 뒤 비교한다 (`홍 길동` = `홍길동`).
3. 방문객은 다른 사람이 남긴 글을 실시간으로(새로고침 없이) 볼 수 있다.
4. 공개 화면에 표시되는 이름은 첫 글자만 남기고 나머지는 `x`로 마스킹하며,
   전화번호 뒤 4자리를 함께 표시해 본인/지인이 알아볼 수 있게 한다.
5. 밴드는 별도의 관리자 페이지에서, 비밀번호 입력 후 전체 글 목록을
   **실명 그대로**(마스킹 없이) 볼 수 있다.
6. 관리자 페이지의 "랜덤 뽑기" 버튼은 아직 뽑히지 않은 글 중 하나를 무작위로
   골라 크게 보여준다 (실명 + 전화 4자리 + 메시지 전문).
   - 한 번 뽑힌 글은 다시 뽑히지 않는다. 새로고침하거나 다른 기기에서
     관리자 페이지를 열어도 유지된다.
   - 뽑힌 글을 서버에서 삭제하지 않는다. 관리자 목록에는 "당첨됨"으로 표시한다.
7. 글 수정/삭제 기능은 만들지 않는다.
8. 관리자 페이지 비밀번호는 실수로 진입하는 것을 막는 수준이면 충분하다
   (고보안 요구 아님).

## 아키텍처

- **프런트엔드**: 정적 HTML/CSS/JS, Vercel에 무료 배포
- **데이터 저장/실시간 동기화**: Firebase Firestore (무료 티어), 브라우저에서
  Firestore SDK로 직접 읽기/쓰기 (별도 백엔드 서버 없음)

이 조합을 택한 이유: 정적 호스팅은 콜드 스타트가 없고, Firestore는 실시간
리스너를 기본 지원해 공연 중 "새 글이 바로바로 보여야 하는" 요구를 서버
운영 부담 없이 만족시킨다.

## 데이터 모델

### `entries/{이름_전화4자리}` — 방명록 글

문서 ID는 `공백 제거한 이름 + "_" + 전화4자리` (예: `홍길동_1234`).
같은 조합으로 다시 쓰면 같은 문서를 덮어쓰려는 시도가 되고, 보안 규칙이
수정을 막으므로 서버 단에서 중복이 차단된다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `name` | string | 공백을 모두 제거한 이름 (예: "홍길동") |
| `phone4` | string | 전화번호 뒤 4자리 숫자 (예: "1234") |
| `message` | string | 방명록 메시지 |
| `createdAt` | timestamp (서버 시각) | 정렬/최신순 표시용 |

### `picks/{entries 문서 ID}` — 당첨 기록

| 필드 | 타입 | 설명 |
|---|---|---|
| `pickedAt` | timestamp (서버 시각) | 뽑힌 시각 |

문서 ID가 곧 뽑힌 글의 ID다. 같은 글에 대한 두 번째 생성은 수정으로
간주되어 규칙에서 거부되므로, 관리자 기기가 여러 대여도 중복 당첨이 불가능하다.

## 화면 구성

### `index.html` — 공개 방명록 페이지

- 작성 폼: 이름, 전화번호 뒤 4자리, 메시지 → 제출 시 `entries/{이름_전화4자리}` 생성
  - 같은 ID의 문서가 이미 있으면 "이미 방명록을 남기셨어요." 안내
  - 등록 성공 시 "방명록이 등록되었어요!" 안내 후 폼 초기화
  - 제출 중에는 버튼 비활성화 (더블클릭으로 인한 오안내 방지)
- 목록: `createdAt` 내림차순, `onSnapshot`으로 실시간 구독
- 항목 표시: 마스킹된 이름 + 전화 4자리 + 메시지
  - 마스킹 규칙: 첫 글자 + 나머지 글자 수만큼 `x` (예: `홍길동` → `홍xx (1234)`).
    2글자 성씨는 근사치로 첫 글자만 인식.

### `admin.html` — 관리자(밴드) 랜덤 뽑기 페이지

- 최초 진입 시 비밀번호 폼. 통과 전에는 목록/버튼 비노출 (클라이언트 측 비교).
- 통과 후: `entries`와 `picks`를 모두 실시간 구독
  - 전체 목록을 실명 그대로 표시 (`홍길동 (1234)` + 메시지), 뽑힌 글은 "당첨됨" 표시
- "랜덤 뽑기" 버튼: 아직 뽑히지 않은 글 중 무작위 1개 선택 →
  `picks/{id}` 생성에 성공한 경우에만 결과를 크게 표시
  - 생성 실패(다른 기기에서 먼저 뽑음 등) 시 "다시 눌러주세요" 안내
  - 뽑을 글이 없으면 버튼 비활성화

## 보안 및 검증 (Firestore Security Rules)

- `entries`: 누구나 `read`, `create`. `update`, `delete`는 전면 차단.
  - `create` 검증: 필드는 `name`, `phone4`, `message`, `createdAt`만 허용
  - `name`: 1~20자, `/` 미포함 (문서 ID에 쓰이므로)
  - `phone4`: 정확히 4자리 숫자
  - `message`: 1~200자
  - `createdAt`: 서버 타임스탬프 강제
  - 문서 ID가 `name + "_" + phone4`와 일치해야 함 (임의 ID로 중복 우회 방지)
- `picks`: 누구나 `read`, `create`. `update`, `delete`는 전면 차단.
  - `create` 검증: 필드는 `pickedAt`만, 서버 타임스탬프 강제,
    같은 ID의 `entries` 문서가 존재해야 함

## 알려진 한계 (합의된 트레이드오프)

- 이름을 살짝 바꾸거나(`홍길동2`) 다른 번호를 넣으면 중복 작성을 막을 수 없다.
  로그인 없는 구조의 한계이며, 무대 호명 시 본인 확인으로 보완한다.
- 관리자 비밀번호는 클라이언트 코드에 평문으로 있어 개발자 도구로 확인 가능하다.
  기술을 아는 사람이 `picks`에 직접 기록해 특정 글을 "이미 뽑힘"으로 만들 수 있다.
- 실명이 DB에 그대로 저장되며, Firestore 읽기 권한이 공개이므로 개발자 도구로
  실명 조회가 가능하다. (운영자 판단으로 감수)

## 에러 처리

- 필드 미입력/형식 오류는 제출 전 클라이언트에서 막고 안내 메시지 표시
- Firestore 쓰기 실패 시 "등록에 실패했습니다. 다시 시도해주세요." 안내
  (`permission-denied`는 동시 제출로 인한 중복으로 간주해 중복 안내)

## 배포

1. Firebase 프로젝트 생성, Firestore 활성화, 웹 앱 등록 후 설정 키 발급
2. 위 Security Rules 배포
3. Vercel에 정적 파일 배포 → `https://<프로젝트명>.vercel.app` 링크 생성
4. 해당 링크를 QR코드 등으로 공연 당일 공유

## 테스트 방법

- 순수 로직(마스킹, 이름 정규화/ID 생성, 입력 검증, 랜덤 뽑기 후보 선정)은
  `node --test` 단위 테스트
- 로컬 정적 서버(`npx serve`)로 여러 탭을 열어 실시간 반영, 중복 작성 차단,
  당첨 글 재추첨 제외(새로고침 후에도)를 수동 확인
- Vercel 배포 후 실제 URL에서 최종 확인 (모바일 브라우저 포함)

## 범위 밖 (Out of scope)

- 글 수정/삭제, 신고, 욕설 필터링 (중복 작성 시 수정 허용 여부는 추후 결정)
- 회원가입/로그인, 전체 전화번호 수집
- 공연 이후 장기 운영, 커스텀 도메인
